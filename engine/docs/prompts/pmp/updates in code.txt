You are right. The issue is **not the table headings**. Your table structure can stay.

The missing layer is a **Query Router + Table Access Protocol** that tells the LLM:

1. what the user is actually asking,
2. which life-event group or groups it belongs to,
3. which houses are required,
4. which principal cusp or cusps to inspect,
5. which tables to pull from your existing packet,
6. when to run one-track vs multi-track judgment,
7. when to ask clarification,
8. when to use KP core logic even if no exact event label exists.

This is important because KP itself says that for answering a query, a **group of houses** is considered, one house becomes the **principal house**, and the sub-lord of that principal house becomes the deciding factor. The text also says no house or planet is universally good or bad; it depends on the matter being judged. So your engine must first understand the **matter judged**, not blindly force the query into one static rule ID.  

## The correction to your idea of Rule IDs

Do **not** make Rule ID a hard gate at the routing stage.

Make Rule IDs a **trace label**, not the first decision-maker.

Better structure:

```text id="vnhx8u"
User question → Query Router → Candidate House Groups → Principal Cusp Selection → Existing Packet Tables → KP Core Rules → Event Rule ID if available → Verdict
```

So if the user asks something unclear like:

```text id="6tw2iy"
Will things improve?
```

The engine should not fail immediately because no exact Rule ID exists. It should classify it as **vague/general**, then inspect whether the user’s context points to career, marriage, finance, health, property, litigation, travel, or multiple groups.

If it cannot identify the object, then it asks a clarification.

But if the user says:

```text id="cbfx57"
Will I get a job abroad?
```

That belongs to **two groups**, not one:

* job/employment: 2, 6, 10
* foreign travel/foreign residence: 3, 9, 12

The engine must run a **combined judgment**. It should not choose only career or only travel.

```text id="d9qudo"
- Should I buy this house or another?

- Will I get a job abroad?

- What will happen?

- Is this period good?
```

# Add this: Candidate group scoring

```text id="g1f9os"
## CANDIDATE GROUP SCORING

For every user query, generate candidate event groups and score them.

Scoring:
+5 if the user explicitly names the event.
+4 if the main noun maps directly to a house group.
+3 if the verb maps directly to an event action.
+2 if the timeframe implies a timing question.
+2 if the object implies another person or derived houses.

+1 if the DBA/RP active houses support the group.
-3 if the group requires assumptions not stated by the user.

Routing decision:
- If one group scores 70% or higher and is 15 points above others: use SINGLE-TRACK.
- If two or more groups are within 15 points: use MULTI-TRACK.
- If no group reaches 40%: ask clarification.
- If the query is broad but the user asks for general reading: use DBA/RP active-house scan.
```

This removes vague words like “most relevant” and gives the LLM deterministic routing.

# Add this: Clarification protocol

You do not want the model to ask too many questions. But sometimes it must.

```text id="cxjs8w"
## CLARIFICATION PROTOCOL

Ask clarification only when the event object cannot be identified.

Do not ask clarification if:
- the event is clear,
- the group can be inferred,
- multiple groups can be judged as tracks,
- the user asks a broad general reading.

Ask one short clarification if:
- the user says “will it happen?” without saying what “it” is,
- the user says “is this good?” without naming the area,
- the query could produce opposite house logic and no context is available.

Clarification format:
“Which area should I judge: career, marriage, finance, property, health, travel, legal matter, child, or relationship?”

If user refuses clarification, run GENERAL DBA/RP ACTIVE-HOUSE SCAN and clearly say:
“No exact event was specified, so this is not an event-specific KP verdict.”
```

# What this does to Rule IDs

Use three levels of rules:

```text id="ofdsy6"
## RULE ID SYSTEM

A. CORE KP RULES
Always active.
Examples:
- CORE-CSL-001: Principal cusp sub-lord decides promise.
- CORE-SIG-001: Use relevant house significators.
- CORE-RETRO-001: Principal CSL retro/star-retro blocks promise.
- CORE-RP-001: Ruling planets select fruitful significators.
- CORE-DBA-001: Event occurs in period of relevant significators.
- CORE-TRANSIT-001: Transit triggers only after promise.

B. EVENT HOUSE RULES
Used when exact event category is identified.
Examples:
- EVENT-JOB-001: Employment = 2, 6, 10 / 10th cusp.
- EVENT-MARRIAGE-001: Marriage = 2, 7, 11 / 7th or 11th cusp as packet rule states.
- EVENT-FOREIGN-001: Foreign travel = 3, 9, 12 / 12th cusp.

C. INFERRED ROUTING RULES
Used when the event is not in the exact dictionary but the house meaning is clear.
Example:
- INFERRED-FINANCE-001
- INFERRED-COMMUNICATION-001
- INFERRED-STATUS-001

No exact EVENT rule ID is not a failure.
Failure occurs only if:
- no event object can be identified,
- no relevant house group can be inferred,
- mandatory packet tables for the selected group are missing.
```

This is the most balanced solution: deterministic but not brittle.
