## 8. TRACK TYPE CLASSIFICATION

Every track in a multi-domain question must be labeled:

### Essential Track

The compound event fails if this track fails.

Examples:
- Employment in “Will I get a job abroad?”
- Marriage in “Will I marry this person?”
- Property sale in “Will property sale bring profit?”

### Modifier Track

This describes the type, location, condition, or special feature of the event.
If modifier fails, the main event may still happen without that modifier.

Examples:
- Foreign company vs physical foreign relocation
- Love-marriage quality
- remote work with foreign client
- government connection
- partner background

### Outcome Track

This describes the result after the event.
If outcome fails, event may still happen but may not give the desired benefit.

Examples:
- Profit after sale
- happiness after marriage
- stability after job
- gain after court settlement

Final synthesis must state each track separately:

- Main event: Promised / Denied / Delayed / Mixed
- Modifier: Supported / Not supported / Weak
- Outcome: Beneficial / Neutral / Loss / Mixed

Do not deny the main event merely because a Modifier or Outcome track fails.

## 13. CORE KP EXECUTION ORDER

For every track, apply this exact order.

### Step 1 — Select principal cusp

Identify the principal cusp for the question or track.

For compound questions, identify multiple principal cusps.

### Step 2 — Read principal cusp sub-lord

From KP PLACIDUS CUSPS, read:
- cusp longitude
- sign lord
- star lord
- sub lord
- sub-sub lord if available

The principal cusp sub-lord is the first decision gate.

### Step 3 — Determine relevant and opposing houses

Relevant houses = houses that support the event.

Opposing houses = houses that deny, obstruct, reverse, or delay the event only if defined by:
- supplied KP rule extract,
- default event rule,
- event-specific denial table,
- or packet-defined negative house group.

If opposing houses are not defined, do not invent them.

### Step 4 — Promise gate

Promise passes only if:

1. principal cusp sub-lord is available;
2. principal cusp sub-lord signifies at least one required house;
3. principal cusp sub-lord is not disqualified by retrograde logic;
4. event-specific essential conditions are satisfied;
5. defined opposing houses do not create a hard fail.

If promise gate fails, do not give timing.

Output:
PROMISE DENIED

or

PROMISE BLOCKED

with evidence.

### Step 5 — Retrograde gate

Check:
- Is principal cusp sub-lord retrograde?
- Is principal cusp sub-lord in the star of a retrograde planet?
- Are DBA lords retrograde?
- Are DBA lords in the sub/star of retrograde planets?
- Is the transit trigger retrograde or touching a sensitive point during retrogression?

If supplied rule says retrograde blocks, block it.

If supplied rule says retrograde delays, mark delay.

If no retrograde rule is supplied, record the retrograde condition but do not invent an exception or denial.

### Step 6 — Significator ranking

Use KP HOUSE SIGNIFICATORS A/B/C/D.

Rank:

A. Planets in star of occupants of relevant houses
B. Occupants of relevant houses
C. Planets in star of owners of relevant houses
D. Owners of relevant houses
E. Nodes representing relevant significators
F. Supported aspects only if packet allows
G. Position Status TRUE only if packet defines and activates it

Do not let auxiliary factors override A/B/C/D unless the packet explicitly says so.

### Step 7 — Node agency

For Rahu/Ketu, decode in this strict order:

1. conjunction
2. aspect, only if packet supports
3. star lord
4. sign lord
5. ruling planet replacement, only if supported

Never jump directly to sign lord when higher-priority agency exists.

State exactly what the node represents and which houses it delivers.

If node agency table is missing, do not use nodes as agents.

### Step 8 — DBA timing gate

Read Dasha, Bhukti, Anthra, and Sookshma if available.

A period can deliver only if:

- promise gate passes;
- DBA lord is a significator of the event houses;
- DBA lord is not blocked by retrograde logic;
- DBA lord receives ruling planet confirmation directly or through star/sub/node/conjunction agency;
- Anthra supports the event;
- transit agrees for specific timing.

If Dasha supports but Bhukti denies: period does not deliver cleanly.

If Dasha and Bhukti support but Anthra denies: event does not materialize in that Anthra.

If DBA supports but transit does not: promise exists but timing is not active.

### Step 9 — Ruling planet gate

Use judgment moment ruling planets primarily.

Ruling planets include:
- Day Lord
- Ascendant Sign Lord
- Ascendant Star Lord
- Ascendant Sub Lord
- Moon Sign Lord
- Moon Star Lord
- Moon Sub Lord

- DBA lords

- node representation,
- conjunction if packet supports.

Do not say “event will happen now” without RP support.
